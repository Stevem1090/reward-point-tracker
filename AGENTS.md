- Push notifications use Firebase Cloud Messaging via the connector gateway: `send-push-notification` edge function + `push_tokens` table + `public/firebase-messaging-sw.js` (scope /firebase-cloud-messaging-push-scope). Why: old VAPID/sw.js system was unreliable on installed phone apps.
- PWA is manifest-only (no app-shell service worker); `public/sw.js` is a kill-switch for the retired worker. Why: avoid stale cached app versions.
- Background task completion from push notifications uses short-lived, task-specific HMAC tokens handled by `task-notification-action`. Why: complete only the notified task without exposing a reusable user session.
- Task reminder input and display use `Europe/London` explicitly. Why: keep selected times stable across device timezone differences and GMT/BST changes.

- Multi-family: shared tables carry `family_id` (default `current_family_id()`) with RLS "same family"; membership in `family_members`, invites via RPCs + `send-family-invite`; `FamilyGate` runs `ensure_family` on load. Why: separate households in one app, master controls members.
- App sections are defined once in `src/config/appSections.ts` and reused by the dashboard and navigation. Why: labels, paths, and icons stay synchronized.
- In-app feedback uses the Radix toast system through `use-toast`/`lib/toast`; Sonner is not mounted. Why: match the single bottom-centre Squirrel It snackbar experience.
- Android app = Capacitor shell loading the published site; native notification code lives in `native/android/` and is copied into the CI-generated `android/` by `scripts/patch-android.mjs` (built by `.github/workflows/android.yml`). Why: no Android Studio needed and the `android/` folder stays disposable.
- Push is split by `push_tokens.platform`: `web` gets Web Push payloads, `android` gets data-only high-priority messages built by the app's own `MessagingService`; `task-sync` messages keep on-phone backup reminders in step. Why: the native app controls display, actions and backups, while the PWA keeps working unchanged.
- Vinted drafts: the on-site script `src/vinted/vinted-create-draft.js` is a versioned black-box asset loaded with `?raw` and never edited here; it runs in `@capgo/inappbrowser` openWebView (pinned 8.6.14, desktop UA via `User-Agent` header) and reports via `messageFromWebview`. All Vinted IDs come from `src/vinted/vinted-reference-kids.json`. Why: the script is maintained and tested separately by the owner.
- Vinted writing instructions and advisory checks live in the writing module, with seller examples as a raw text asset; description regeneration merges into the latest reviewed item only. Why: keep wording checks separate from approval gates and preserve concurrent seller edits.
- Vinted batch preflight: before every item the host navigates to /items/new, injects the black-box `src/vinted/vinted-page-probe.js` and acts on its final `vinted:pageStatus`; retry/ladder/pause rules live in `src/vinted/batch.ts`. Why: Vinted error pages wipe injected scripts, so recovery must be driven by the app and never re-send a saved item.
- Vinted photos: item.images stay the untouched originals (add order, EXIF baked in); order/rotation is a separate arrangement in `src/vinted/photos.ts`, rotated from originals only at send time. Why: undo/reset is always possible and the draft script just uploads what it is sent.
- AI edge functions call Google's native Gemini generateContent API via `supabase/functions/_shared/gemini.ts` (model ids live there) with server-only GEMINI_API_KEY; shared error helpers preserve provider statuses. Why: use the owner's Google project directly; older model ids get retired and return 404.
- All Vinted analysis and regeneration in a browser uses one sequential queue with a start gap sized to the Gemini free-tier per-minute limit (ANALYSIS_START_GAP_MS). Why: stay under the quota without claiming a cross-device or project-wide quota guarantee.
